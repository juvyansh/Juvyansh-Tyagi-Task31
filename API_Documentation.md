## Objective

Plan and demonstrate RESTful API endpoints for a To-Do List application. The frontend could be built with React.js, while Express.js handles HTTP requests and responses.

## Task data model

Each task contains:

- `id`: unique identifier generated by the server
- `title`: required, non-empty string
- `description`: optional string
- `completed`: Boolean, initially `false`
- `createdAt`: creation timestamp
- `updatedAt`: most recent update timestamp

Example:

```json
{
  "id": "task-1",
  "title": "Learn Express.js",
  "description": "Understand routes and HTTP methods",
  "completed": false,
  "createdAt": "2026-10-29T12:00:00.000Z",
  "updatedAt": "2026-10-29T12:00:00.000Z"
}
```

## Endpoint details

### 1. Create a task

**Method and route:** `POST /api/tasks`

Request body:

```json
{
  "title": "Study REST APIs",
  "description": "Review HTTP methods and status codes"
}
```

Returns `201 Created` and the newly created task. The server generates the ID. A missing/blank title or a non-string description returns `400 Bad Request`.

### 2. Get all tasks

**Method and route:** `GET /api/tasks`

No request body is required. Returns `200 OK` with a JSON array. Optional filters are supported: `GET /api/tasks?completed=true` and `GET /api/tasks?completed=false`.

### 3. Get one task

**Method and route:** `GET /api/tasks/:id`

Example: `GET /api/tasks/task-1`. Returns `200 OK` and the matching task. If the ID does not exist, returns `404 Not Found`.

### 4. Replace/update a task

**Method and route:** `PUT /api/tasks/:id`

Request body:

```json
{
  "title": "Study Express.js APIs",
  "description": "Finish endpoint documentation",
  "completed": false
}
```

Returns `200 OK` and the updated task. Title must be a non-empty string, description must be a string, and completed must be a Boolean. A missing task returns `404 Not Found`.

### 5. Partially update a task

**Method and route:** `PATCH /api/tasks/:id`

Example request body:

```json
{
  "completed": true
}
```

Only supplied fields are changed. Returns `200 OK` and the updated task. Unsupported fields or invalid values return `400 Bad Request`; a missing task returns `404 Not Found`.

### 6. Delete a task

**Method and route:** `DELETE /api/tasks/:id`

No request body is required. Returns `204 No Content` when deleted, or `404 Not Found` when there is no task with that ID.

## HTTP status codes

- `200 OK`: read or update succeeded.
- `201 Created`: task created successfully.
- `204 No Content`: task deleted successfully; no response body.
- `400 Bad Request`: invalid JSON or invalid field values.
- `404 Not Found`: requested task does not exist.
- `500 Internal Server Error`: an unexpected server-side error occurred.

## How the APIs support CRUD

- **Create:** `POST /api/tasks`
- **Read:** `GET /api/tasks` and `GET /api/tasks/:id`
- **Update:** `PUT /api/tasks/:id` and `PATCH /api/tasks/:id`
- **Delete:** `DELETE /api/tasks/:id`

## RESTful design reasoning

The API uses the noun `tasks` to represent a collection of resources. HTTP methods describe the operation, while `:id` identifies a specific task. JSON is used for the data format. The server validates incoming data and returns meaningful status codes, which helps the React client handle success and error cases consistently.

## Potential implementation challenges

1. Generating unique IDs and avoiding accidental duplicate identifiers.
2. Validating client-submitted data rather than trusting the frontend alone.
3. Returning `404` for IDs that do not exist.
4. Preserving data after server restarts. This demo stores tasks in memory only, so use a database for persistent storage.
5. Configuring CORS if a separately hosted React frontend calls the API.
6. Adding authentication and per-user authorization if multiple users are supported.
7. Centralizing error handling and avoiding exposure of internal stack traces.

## Important limitation of this demo

The deployed version uses an in-memory array to keep setup simple for a first deployment. Any created, updated, or deleted tasks can be lost when the service restarts or redeploys. It is suitable for demonstrating the API contract, not for production storage. A database should be added for persistent data.
